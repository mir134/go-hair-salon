# 文档定位

本文件是业务层唯一规则依据。数据库、API、前端交互均不得自行改变这里定义的业务语义。

# 1. 客户规则

- 手机号作为主要查询条件，但允许为空。
- 同一门店原则上一个手机号对应一个客户。
- 客户软删除，不物理删除历史消费、充值、余额流水。
- 客户修改手机号不得创建新客户。
- 客户详情必须能追溯消费、充值、余额流水、积分流水。

# 2. 服务项目规则

- 服务项目包含名称、分类、标准价格、状态。
- 已产生订单的服务禁止物理删除。
- 订单保存服务名称和成交单价快照，后续修改服务价格不得影响历史订单。
- 停用服务不能创建新消费，但历史订单仍可查看。

# 3. 消费规则

- 所有金额使用整数分。
- 消费必须产生订单和订单明细。
- 消费方式至少支持：现金、微信、支付宝、余额。
- 消费金额、支付方式、操作员工、发生时间必须可追溯。
- 余额消费必须同时写入 balance_transactions。
- 余额不足时拒绝消费，不允许出现负余额。
- 一次消费成功后，不允许直接修改订单金额；需要通过退款/冲正处理。
- 创建订单必须携带 request_id，后端唯一约束保证同一 request_id 只入账一次。
- 支持挂单（先开单后付款）：创建订单时未收款可先挂单（status=pending），挂单不产生任何资金/余额/积分变动。
- 挂单订单结账前可编辑明细（增删服务项目、修改数量），订单金额随明细重算；编辑明细不产生资金变动，但修改单价仍受 3.1 改价权限约束。
- 已结账/已退款/已取消订单的明细不可编辑。
- 挂单订单长期保留，不自动过期或取消（MVP 无定时任务）；管理员可随时手动取消（cancel）。
- 挂单结账（pending → completed）时，余额扣减、余额流水、积分流水必须在同一个数据库事务内完成。
- 直接完成的订单：订单创建、余额扣减、余额流水必须在同一个数据库事务中完成。
- 挂单订单（pending）不计入营业额，结账后才计入。
- 挂单订单可取消（仅 admin），取消后状态置为 cancelled；已结账订单不可取消，只能退款。

## 3.1 改价与折扣

- 成交价可与标准价不同（改价/折扣），但必须记录原始价与成交价差额（discount_amount_cents）。
- 改价/折扣仅 admin 可操作；staff 只能按标准价成交。
- 每次改价必须写 operation_logs（记录操作人、原价、成交价、原因）。
- 改价后订单完成即锁定，不得再改。

# 4. 充值规则

- 充值记录和余额流水必须同时产生。
- 支持充值金额与赠送金额分开记录。
- 金额字段语义（对应 03-DATABASE.md）：`recharge_amount_cents` 充值本金、`gift_amount_cents` 赠送、`actual_amount_cents` 客户实际支付。余额增加 = 充值本金 + 赠送金额。
- 有赠送金额时，本金与赠送分别产生两条 balance_transactions 流水（type=recharge / type=gift），balance_after 连续。
- 充值操作必须记录操作人、支付方式、流水号/幂等键。
- 同一幂等键不能重复入账：`recharge_records.request_id` 唯一约束强制保证，重复请求返回原记录。
- 默认不提供直接删除充值记录；错误充值通过退款/调整流水纠正。

# 5. 退款与调整

- 退款必须关联原订单或原充值记录。
- 退款不得直接覆盖历史金额。
- MVP 仅支持全额退款，退款成功后原订单/充值状态作废（refunded），部分退款暂不实现。
- 退款通过反向流水实现，保证账务可追溯。
- 余额调整仅允许管理员操作，并必须填写原因。
- 余额调整通过 `POST /customers/:id/balance-adjustments` 执行，写 balance_transactions（type=adjustment）；不产生订单，不计入营业额。
- 所有调整必须写 operation_logs。
- 退款、调整、冲正均不得删除原始流水。

# 6. 积分规则

MVP 默认采用简单积分模型：

- 消费产生积分，比例由系统设置 `points_per_yuan` 决定（每消费 1 元获得 N 积分，N 默认 1）。
- 充值默认不产生消费积分。
- 退款按原消费积分进行反向扣减。
- 积分不得低于 0。
- 积分变化必须写 points_transactions。
- 后续可扩展积分兑换，但不纳入第一阶段。

# 7. 员工与权限

- admin：拥有全部后台权限。
- staff：客户查询、新增客户、消费（含挂单/结账）、充值等日常操作；**禁止**订单取消、余额调整、退款、删除客户、系统设置修改、操作日志查看、员工管理、数据恢复。
- 改价/折扣仅 admin 可操作（见 3.1）。
- 所有敏感操作记录 operator_id。
- 权限控制必须同时存在于前端和后端，后端是最终安全边界。

# 8. 营业额统计

- 营业额以实际成交订单为基础。
- 余额消费属于消费订单，应计入营业额。
- 充值金额属于资金流入，不直接等同于营业额。
- 退款应冲减对应营业额。
- 挂单（pending）订单未结账不计入营业额。
- 已取消/已退款订单不能重复计入营业额。
- Dashboard 的统计口径必须与这里一致。

统计口径定义：

- 今日营业额：当日 completed 订单 `paid_amount_cents` 合计，减去当日退款冲减。
- 今日消费单数：当日 completed 订单数量。
- 今日消费人数：当日有 completed 订单的去重客户数。
- 今日新增客户数：当日新建客户数。
- 今日充值金额：当日充值记录 `actual_amount_cents` 合计（不含赠送）。
- 待结账单数：当前所有 pending 挂单订单数量（提醒门店及时结账）。

# 9. 并发与幂等

- 充值、余额消费、退款必须支持幂等。
- 客户端创建订单/充值时携带 request_id，后端在 orders、recharge_records 建立唯一索引强制幂等。
- SQLite 事务是账务一致性的边界。
- 余额扣减必须在事务内完成并校验当前余额。
- 禁止先查询余额、事务外修改余额的实现方式。

# 10. 时间

- 数据库统一存储 UTC（Unix 时间戳或 UTC datetime，全局一致）。
- API 统一使用 ISO 8601 格式传输时间（含时区偏移）。
- 展示层按设备/门店本地时区展示。
- 历史记录不得因为服务重启或时区变化而改变原始发生时间。

# 11. 删除策略

- 核心业务数据默认软删除或状态作废。
- users、customers、services 等可停用；orders、balance_transactions、points_transactions、recharge_records 不允许物理删除。
- “删除”操作必须明确是隐藏、停用还是业务作废，不能用一个 DELETE 同时表达三种语义。
- 具体语义约定：customers/services/tags 使用 deleted_at 软删除；users 使用 status 停用（保留账号记录）；orders 等账务表永不物理删除，作废走 cancelled/refunded 状态。
